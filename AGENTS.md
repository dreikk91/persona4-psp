# Working on this port

Rules for anyone (human or agent) changing the Persona 4 PSP port. Read before touching `port/` or `docs/`.

## What is current

- The code in `port/` and `tools/` is the truth. Documentation describes it; when the two disagree, the code wins and
  the document gets fixed in the same change.
- Current documents: `README.md`, `CHANGELOG.md`, `docs/*.md`. Historical records (old plans, validation reports,
  per-build experiment logs) live in `docs/archive/`. Read the archive only to answer a specific historical question,
  such as "was X already tried?", never as a description of how the port works now.
- A document named after a build (`*_b366.md`) describes that build. Check the build number against
  `#define BUILD` in `port/main.c` before relying on it.
- Runtime controls: `docs/runtime_controls.md` is generated by `python tools/p4_controls.py --md docs/runtime_controls.md`.
  Regenerate it after adding or removing a `p4_*` control; never edit it by hand.

## Changing behaviour

- Do not reintroduce a removed or rejected optimisation without a new argument (a new measurement, a different
  bottleneck). The changelog and `docs/archive/perf_history.md` say what was tried; grep them by switch name first.
- Do not add a runtime switch without a reason to flip it at runtime. A correctness fix is not a switch. An
  experiment that gets a switch is either kept (switch removed, path made standard) or removed (code deleted) once
  it is measured. Diagnostic-only controls (`*_check`, `*_census`, `*_trace`, `p4_probe_*`, `p4_exp_*`) belong in
  the profiling build (`P4_HW_PROFILE`).
- A port table that keeps a game object's pointer (hierarchy, frame, atomic, interpolator, raster) needs that
  object's destroy hook, or must re-check the pointer against a live owner before it dereferences it: the game frees
  models at every field change and the next ones land at the same addresses (issue #24). After such a change run
  `tools/psp_stress.py` (poisoned frees, field warps).
- Keep compatibility fallbacks that real data needs (missing offline caches, geometry a fast path refuses).
- One fact in one place. Link instead of copying numbers between documents.
- After an architectural change, update the document that describes that part in the same commit.

## Measuring

- Say where a number comes from: **PSP** (real hardware, 333 MHz, build and scene named) or **PPSSPP**. PPSSPP
  timings are not performance results; PPSSPP hides cache, bus, GE and alignment behaviour (see `CLAUDE.md`).
- Never compare profiled (`profmode t`) and unprofiled numbers.
- Regression check in PPSSPP: build with `tools/psp_hw_debug.py --out build/psplink_bNNN`, run a route
  (`P4_ROUTE=tools/routes/battle_b177.txt`, `tools/routes/margaret.txt`) with `tools/psp_run.py`, compare the
  screenshot, the `hwperf` lines and the `TRACE` lines of `p4_hwdbg.log` against the previous build. Routes drift
  with battle RNG; a desynchronised route is not a regression by itself.
- A release (`--release`) build must be linked too: profiling builds hide release-only link breaks.
